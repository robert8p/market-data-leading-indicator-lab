# Deployment — upgrading directly from v1.0.2 to v3.0.1

## Before deployment

Do not delete the existing Supabase project or its data. Migrations 002 and 003 are additive and preserve the original bars and runs.

Create a backup or point-in-time restore checkpoint in Supabase before any production migration.

## Existing Render service compatibility

This release deliberately preserves the original v1.0.2 Render service names `market-data-lab-web` and `market-data-lab-worker`, so a Blueprint sync updates them in place. Only `market-data-crypto-stream` is new. Do not rename the existing services before syncing.

## 1. Replace the GitHub repository

1. Download and unzip the v3.0.1 package.
2. Replace the repository contents with the package contents.
3. Commit and push to the branch connected to Render.
4. Do not manually rerun `001_initial.sql`; the migration runner tracks migration filenames and applies only missing migrations.

## 2. Required secrets

### Web service

- `DATABASE_URL`
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `APP_PASSWORD`
- `SESSION_SECRET` — generated by Render in the Blueprint

### Historical collection worker

- `DATABASE_URL`
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `ALPACA_API_KEY`
- `ALPACA_API_SECRET`
- `MASSIVE_API_KEY`
- `SEC_USER_AGENT` — use a descriptive value containing your name and contact email
- `TWELVEDATA_API_KEY`
- `COINGECKO_DEMO_API_KEY` — optional; the public/demo path is still rate-limited

### Crypto-stream worker

- `DATABASE_URL`
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

The configured exchange WebSocket feeds do not require trading credentials. Do not add exchange withdrawal or trading keys to this application.

## 3. Important defaults

- `ALPACA_FEED=sip`
- `EQUITY_CONTEXT_SCOPE=all`
- `CRYPTO_RAW_CORE_ENABLED=false`
- `CRYPTO_STREAM_MAX_DYNAMIC_TARGETS=30`
- `CRYPTO_RAW_SEGMENT_MINUTES=15`
- `CRYPTO_ORDER_BOOK_DEPTH=20`
- `CRYPTO_DERIVATIVES_SYMBOL_CAP=300`

For a cheaper first deployment, change `EQUITY_CONTEXT_SCOPE` to `captured`. This limits Massive context jobs to symbols with neutral capture windows.

## 4. Deploy in this order

### A. Web service first

Deploy the existing `market-data-lab-web` and wait for the pre-deploy migration to finish.

Verify:

```text
https://<your-web-service>/health
```

Expected fields include:

- `status: ok`
- `version: 3.0.1`
- `role: collection_only`

Do not deploy the workers until this succeeds.

### B. Historical collection worker

Deploy the existing `market-data-lab-worker`. Confirm the log contains:

```text
Collection worker started
```

The worker should be able to query `capture_windows` before entering its loop.

### C. Crypto-stream worker

Deploy `market-data-crypto-stream` after the migrations and historical worker are healthy.

The stream requires venue mappings in `crypto_venue_symbols`. The collection worker creates these during crypto enrichment. If mappings do not yet exist, the stream remains alive and refreshes its target set until they appear.

## 5. Reuse the original run

Because only v1.0.2 has been deployed, the safest path is:

1. Log in to the web app.
2. Open the existing completed 30-day run.
3. Select **Mine/enrich stored bars** once.
4. The run moves through:
   - `collecting` — verifies original bar/catalogue tasks are terminal;
   - `capture_scan` — creates neutral acquisition windows from stored bars;
   - `enrichment` — gathers targeted microstructure and context;
   - `ready` — collection is finished.
5. Do not repeatedly press the enhancement button while the run is active.

This path does not recollect completed one-minute bars.

A new run can also be started. A new run collects fresh bars and then automatically proceeds through capture scanning and enrichment.

## 7. Prospective crypto-data expectation

Historical candles, some trades, funding and open-interest series can be backfilled. Full order-book update history cannot be recreated from the public live streams after the fact. The one-second cross-venue microstructure history starts accumulating when the crypto-stream worker connects.

Any stream outage is recorded. Missing raw depth updates remain a disclosed gap.

## 8. Pause, resume and failures

- **Pause** prevents new work being claimed and releases the current atomic task at its next checkpoint.
- **Resume** continues from committed cursors.
- **Retry failed partitions** requeues failed/cancelled partitions without deleting completed rows.
- **Cancel all jobs** cancels queued, running and paused historical runs; it does not delete collected data.
- Restarting a Render worker does not reset the run.

The prospective crypto stream is continuous rather than run-scoped. Stop or suspend its Render service to stop live collection.

## 9. Storage monitoring

Monitor:

- Postgres database size and IOPS;
- `crypto_microstructure_1s` growth;
- private bucket size;
- raw object count and average segment size;
- worker memory and reconnect frequency.

If growth is excessive:

1. keep `CRYPTO_RAW_CORE_ENABLED=false`;
2. reduce `CRYPTO_STREAM_MAX_DYNAMIC_TARGETS`;
3. raise the broad trigger threshold;
4. increase `CRYPTO_AGGREGATION_SECONDS` from 1 to 5;
5. reduce core symbols or venues;
6. use `EQUITY_CONTEXT_SCOPE=captured`.

## 10. Rollback

A code rollback to v1.0.2 will leave the new tables in Supabase but will not use them. Do not drop migrations 002/003 during an emergency rollback. Restore the prior Git commit and redeploy the web/worker services.

The live crypto-stream service does not exist in v1.0.2; suspend or delete that Render service during rollback.
